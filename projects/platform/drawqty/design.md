# DrawQty 디자인

## 아키타입

- **웹 홈 골격: 도구형 4단계 흐름.** 이유: 이 사이트는 업체 홈페이지에 붙는 계산 도구라 랜딩형 홈이 없다. 첫 화면이 곧 업로드 화면이다. 화면마다 골격을 바꾼다. 업로드는 **좌정렬 분할**(드롭 영역 좌, 도면 종류와 산출 대상 우), 인식 확인은 **뷰어 + 목록 마스터-디테일**(좌 도면, 우 인식 목록, 하단 합계 바), 결과는 **요약 2열 + 표 + 차트**, 견적 요청은 **폼 + 고정 요약 패널**이다. 인접한 두 화면이 같은 골격이 아니다.
- **실제 서비스로 설계한다(사용자 지시).** 홍보 홈페이지가 아니라 업체가 내부적으로 운영하는 웹 서비스이므로 회사 소개, 시공 사례 같은 사이트 메뉴, 푸터, `사용자 화면 | 관리자 페이지` 전환 스위치를 두지 않는다. 상단 바는 서비스 헤더(로고, 작업 영역 이름, 계정)이고 두 앱은 URL과 계정이 따로다.
- **관리자 셸: C2 워크벤치, 좌측 사이드바.** 이유: 사용자 지정으로 관리자는 항상 좌측 사이드바다(2026-10-07, 처음 C3 상단 바로 만들었다가 바꿨다). 업체 한 곳이 접수 건을 처리하는 단일 테넌트 콘솔이고 IA가 두 개라 C2의 풀블리드 본문이 맞는다. 행을 누르면 우측에 디테일 패널이 열리는 마스터-디테일이다.
- **배제한 후보 (웹 홈):** 검색 우선 히어로는 도메인이 검색이 아니라 파일 업로드라서 맞지 않다. 풀블리드 미디어 히어로는 건설 장비 사진이 필요한데 맞는 사진을 직접 확인할 수 없고(사진 매핑 참고), 첫 화면에 업로드 영역이 바로 보여야 한다는 spec의 핵심과 어긋난다.
- **배제한 후보 (관리자):** C1은 포화이고 테넌트를 가로지르는 슈퍼관리자가 아니다. C4는 IA가 2단계가 아니라서 섹션 리스트 컬럼이 비는다. C3 상단 바는 사용자 지정으로 신규 배정 금지다.
- **이 아키타입에서 쓰지 않는 부품:** 가운데 정렬 히어로, 같은 카드 3열, CTA 띠, 이용 흐름 설명 섹션(진행 표시가 그 역할이다), 후기와 신뢰 수치 블록. KPI 카드 4개 병렬(요약은 크기가 다른 2개). 관리자에는 상단 내비, 드로어, 헤더 시계, 대시보드 화면이 없다.
- **앱과 관리자의 분리:** 사용자 화면은 `/platform/drawqty`, 관리자는 `/platform/drawqty-admin`으로 URL이 따로다. `-admin`에는 자체 docs, 스타일이 없고 이 프로젝트의 토큰을 상속한다. 관리자 화면 코드는 `components/admin/`에 있다. 두 URL은 브라우저 `localStorage`로 업로드와 견적 요청을 공유한다(백엔드 없음).

## 적용 규칙

해석: DWG 도면 물량 산출 웹 도구 for 견적을 검토하는 건설사 담당자와 접수 건을 처리하는 업체 관리자. 사용자 화면 다이얼 V4 / M3 / D6, 관리자 다이얼 V3 / M2 / D7.

- 읽은 skill: `mockup-craft` SKILL.md, `references/anti-slop.md`, `web.md`, `console.md`. `스타일:`, `디자인시스템:`, `프리미엄디테일:` 줄은 없다.
- 사용자 화면 V4 / M3 / D6: SKILL.md 2절의 웹 목록(4/3/6)을 따랐다. 도면 뷰어와 표가 반이라 밀도를 올렸고, 골격 파격은 화면별 골격 교체로 충분해 4에 둔다. 모션은 단계 전환, 패널, 토스트, 분석 진행 막대뿐이다.
- 관리자 V3 / M2 / D7: 콘솔 목록(3/2/8)과 상세(3/2/6)의 중간. 표와 상세 패널이 반반이다.
- 숫자 규칙: 면적 ㎡, 체적 ㎥, 길이와 높이 m는 소수점 1자리, 천 단위 구분, 표에서는 오른쪽 정렬과 `tabular-nums`. 큰 숫자에는 단위를 붙이지 않고 라벨에 `(㎡)`로 옮긴다.
- 산출식: 비계 면적 = 외벽 구간 길이 x 높이. 동바리 체적 = 슬래브 면적 x 내부 높이. 구간 8~10개 중 확인 필요 2개와 수동 수정됨 1개는 1층에 둔다.
- 카피는 해요체 하나로 통일한다. 관리자 라벨과 버튼은 명사형이다. 개략 물량 안내 문구는 결과 화면 하단 바와 견적 요청 화면 상단에 항상 보인다.
- 상태 색 의미는 고정이다. 인식 신뢰도: 높음 초록, 확인 필요 주황, 수동 수정됨 파랑. 견적 상태: 신규 파랑, 검토 중 주황, 견적 발송 초록.

## Tokens, 팔레트

팔레트 구성 4: **틴티드 뉴트럴(콜드 슬레이트).** 무채색이 아니라 청회색을 머금은 뉴트럴이고 계층은 명도로 만든다. 브랜드 잉크(딥 스틸 네이비)는 주 버튼, 현재 단계, 관리자 상단 바에만 쓴다. 이유: 건설, 산업 도메인의 차분한 톤이 spec 지시이고, 도면 위 오버레이가 신뢰도 상태색(초록, 주황, 파랑)을 직접 쓰므로 브랜드 액센트를 따로 키우면 파랑 상태색과 충돌한다. 같은 platform 카테고리의 직전 프로젝트들(dressday 1, veli 5)과 다른 구성이다. teefinder(b2b)도 4지만 따뜻한 그린 슬레이트이고 여기는 차가운 스틸 블루 슬레이트다.

`styles/drawqty.css`의 `.drawqty` 스코프, 접두어 `--dq-`.

| 토큰 | 값 | 용도 |
| --- | --- | --- |
| surface | `#ffffff` | 페이지, 패널, 표 |
| soft | `#f3f5f8` | 입력 바닥, 표 헤더, 호버 |
| soft-2 | `#e8ecf1` | 칩, 구분 면 |
| line / line-strong | `#dbe1e8` / `#c2cbd5` | 헤어라인 / 입력 테두리 |
| ink / ink-2 / ink-3 | `#16202b` / `#434f5c` / `#5b6773` | 본문 3단 (ink-3도 soft 위 AA) |
| brand | `#1d3a57` | 주 버튼, 현재 단계 |
| bar | `#17293b` | 관리자 상단 바 (내비 면만 짙은 색, 본문은 흰색) |
| paper | `#fbfcfd` | 도면 바탕 |

상태색은 `--dq-green/orange/blue/red/gray`와 각각 `-fg`(흰 바탕 AA), `-bg`(배지 바닥). 도면 오버레이는 상태색 본색을 쓴다.

## Shape

- 사용자 화면: 패널 12px, 버튼과 입력 8px, 칩 6px. 카드는 그림자 없이 헤어라인, 토스트와 팝오버만 `0 1px 2px, 0 8px 24px` 옅은 2단.
- 관리자: 패널 10px, 버튼과 입력 6px, 배지 6px(고정 크기). 사용자 화면보다 한 단 각지게 둬서 같은 제품의 다른 면임을 드러낸다.
- 상태 칩은 글자 수와 무관하게 고정 폭, 가운데 정렬(`수동 수정됨`에 폭을 맞춘다).

## Typography

Pretendard 단일. 사용자 화면 본문 **14px / 22px / 400**, 페이지 제목 28px / 36px 700, 섹션 제목 18px / 26px 600, 라벨 13px 500, 캡션 12px. 핵심 숫자만 700, 나머지 숫자는 600. 관리자 본문 **13px / 19px**, 표 셀 13px, 표 헤더 12px 500, 페이지 제목 20px 600. 전부 `tabular-nums`, `keep-all`.

앞선 프로젝트와 다르게 한 것: 본문 14/22(번진 15/22, teefinder 앱 16/24, 14/21과 모두 다름), 관리자 본문 13/19(번진 13.5/20과 다름).

## 사진 매핑

사진을 쓰지 않는다. 이 도구의 시각 요소는 도면 SVG와 표, 차트다. 홈페이지 래퍼에도 현장 사진 자리를 만들지 않았다(맞는 사진을 직접 확인해 매핑할 수 없다). 로고는 글자 모노그램 타일이다. 사진 요청 목록 없음.

## 반응형 기준

기준 폭 393 / 768 / 1024 / 1440. 모바일 우선, 본문 `max-w-[1240px]`, 거터 모바일 16px / 데스크톱 32px.

- 헤더: 56px 한 줄. 로고, 작업 영역(물량 산출), 우측 계정. 모바일은 계정 이름만 숨긴다.
- 진행 표시: 데스크톱은 4단계 가로 목록(번호 + 단계명). 모바일은 4칸 막대(단계명은 바로 아래 화면 제목이 대신한다).
- 업로드: 1024 이상 좌 7 / 우 5 분할, 미만은 드롭 영역 위 설정 아래.
- 인식 확인: 1024 이상 도면 좌, 목록 우 380px. 미만은 도면 위, 목록 아래 한 열. 하단 합계 바는 `sticky bottom-0` 불투명, 모바일에서는 숫자 3개만 남기고 확인 필요 건수와 버튼은 두 번째 줄.
- 결과: 1024 이상 요약 2열 + (표 8 / 차트 4). 미만은 전부 한 열이고 표는 `overflow-x-auto`, 최소폭 560.
- 견적 요청: 1024 이상 폼 7 / 요약 패널 5(sticky). 미만은 요약 패널이 폼 위로 올라간다.
- 하단 고정 바는 전부 불투명이고 `backdrop-blur`가 없다. 터치 타깃은 모바일에서 44px 이상.

## 셸 레이아웃 (관리자)

- 좌측 사이드바 232px, `sticky h-dvh`, 배경 `--dq-bar`(내비 면만 브랜드 짙은 색). 위에서부터 브랜드 블록(DQ 마크, `DrawQty 관리`, 한결시스템 표기), 메뉴 2개(견적 요청에 신규 건수, 업로드 도면, 활성은 아이콘 fill + 한 톤 밝은 면), 하단 운영자 칩. 별도 헤더 바와 시계, 전역 검색은 없다(검색은 각 화면 표 위에 둔다).
- 본문은 흰색, 풀블리드(`max-w-none`), 거터 32px. 우측 디테일 패널 360px(`xl` 1280 이상 표 옆, 미만은 표 아래로 내려간다).
- 드로어 없음. `lg` 1024 미만에서 사이드바는 상단 짙은 띠(브랜드 + 가로 탭)로 접힌다.
- 사용자 화면 셸과의 차이는 서비스 헤더(흰 바탕, 하단 헤어라인) 대 관리자 바(짙은 면)다. 사용자 화면에는 관리자로 가는 진입점이 없고 관리자에도 사용자 화면으로 가는 스위치가 없다(실제 서비스처럼 주소와 계정이 다르다).

## 표 밀도, 컬럼 예산

열 상한 6. 행 높이 56px(견적 목록, 이름 + 보조 줄), 업로드 도면 52px. 패널을 옆에 두는 것은 1280px 이상(`xl`)이고 그 미만은 패널이 표 아래로 내려간다.

- 견적 요청 표(1440px에서 사이드바 232와 거터 64를 뺀 본문 1144, 패널 360을 열면 표 약 768px): 접수번호 + 요청일 보조 줄 136, 업체명 + 현장명 보조 줄은 남는 폭, 연락처 120, 비계 면적 (㎡) 104 우측 정렬, 동바리 체적 (㎥) 116 우측 정렬, 처리 상태 96. 고정 열 합계 572, 최소폭 752.
- 업로드 도면 표(패널 열림): 파일명 + 관리 번호 보조 줄은 남는 폭, 업로더 120, 업로드 일시 140, 크기 (MB) 88 우측 정렬, 인식 결과 128. 5열, 최소폭 640.
- 결과 표(사용자, 8열 영역 약 780px): 층 64, 구분 + 대상 보조 줄 200, 길이 (m) 96, 면적 (㎡) 112, 높이 (m) 88, 수량 120. 합계 680 + 패딩, 최소폭 560 이하에서 가로 스크롤.
- 좌우 높이가 다른 그리드에는 `items-start`를 준다.

## Motion

- 단계 전환과 화면 진입: 220ms `cubic-bezier(0.4, 0, 0.2, 1)` standard, 페이드 + translateY 16px. 스태거 없음. (앞선 프로젝트의 420ms expo-out, 280ms, 8px와 다름)
- 패널과 토스트: 관리자 우측 패널 200ms translateX 24px, 토스트 200ms translateY.
- 눌림: 사용자 화면 버튼 `scale(0.98)` 120ms. 관리자는 hover 배경 톤만. (teefinder의 translateY(1px)와 다름)
- 분석 진행: 선형 진행 막대와 단계 문구 전환(3단계, 약 2.7초). `prefers-reduced-motion`에서 진입, 패널, 눌림 애니메이션을 끄고 진행 막대는 즉시 전환한다.
